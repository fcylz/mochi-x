# 云端导入（云端字卡 / 表情包 / 曲库）

现在的实现在**站点源码里**，不是外部脚本：

- `src/js/cloud-import.js`：识别云端 `.json` 链接 → 拉取 → 展开成现有导入框本来就认的格式
- `src/js/chatcard.js`：字卡「批量导入」、表情/图片「链接导入」两个回调接入
- `src/js/music-player.js`：音乐「批量导入」回调接入
- `build.mjs`：`jsFiles` 清单里登记了 `cloud-import.js`

落库、去重、分组、图片压缩转存/入媒体池、音乐落库刷新，全部复用站点**原有**导入管线。
改完源码必须 `node build.mjs` 重新构建。用法与部署见仓库根目录的 `DEPLOY.md`。

## 自检

```bash
node tools/cloud-sync/smoke-cloud-import.mjs
```

Node 层必跑（链接识别、三份云端数据取回与展开、上次地址记忆）；装了 playwright 会额外跑一次
浏览器端到端（起本地服务打开 index.html，真的点一次「批量导入」验证落库）。

## 备选：油猴脚本（桌面自动同步）

`mochi-cloud-sync.user.js` 是另一条路——不装进站点，靠浏览器扩展在**打开页面时自动同步**
（不用手动点导入）。桌面装 Tampermonkey/Violentmonkey 即可，手机基本用不了。

两条路可以并存：站点内的「云端导入」负责随时手动补内容，脚本负责打开即自动同步。
脚本内部用的是同一套站点接口（`ccReloadGroupsAfterExternalWrite`、`mochiMediaTokenize` 等），
互不冲突——两边都做了内容去重，重复导入不会产生重复字卡。

### 分类落位与分组合并（脚本 1.2.0 起，站点同步；1.3.0 补功能分类）

云端分类 → mochi 字卡分类：

| 云端分类 | 落到 mochi 的 | 说明 |
|---|---|---|
| `kaomoji` 颜文字 | **颜文字** tab | 有独立分类 |
| `emoji` emoji | **emoji** tab | 有独立分类 |
| `poke` 拍一拍 | **拍一拍** tab | 载体分类，抽中拼成「TA 拍了拍你 …」，只适合短句 |
| `daily` 日常 / `connect` 连接 / `address` 称呼 / `quotes` 官方语录 / `sweet` 情话 | **主字卡** tab | 都是文本类，各成一组建在同一个 tab 下 |
| `fish` 摸鱼 / `eat` 吃饭 / `period` 经期 / `water` 喝水 / `garden` 花园 / `sync` 同频 / `reach` 伸手 / `cjian` 此间 / `room` 房间 / `piggy` 存钱罐 / `drift` 漂流瓶 / `interact` 互动回应 / `music` 音乐 | **同名功能池** | 1.3.0 新增：写进各功能页自己的抽卡池，**不进聊天通用回复** |

功能分类的 13 个 key 与站点 `chatcard.js` 的 `CC_FUNC_KEYS`、`card-audit.js` 的 `CC_LABEL`
一一对应；脚本里它们不算「载体类型」，所以另开了 `CC_WRITE_TYPES = CC_TYPES + CC_FUNC_TYPES`
做写前校验——只校验 `CC_TYPES` 的话，这些分类会被打回 `defaultWordType`（text），
「该吃饭了」就会被聊天自动回复抽出来。

刻意不映射表情包/图片/语音：云端字卡是纯文本，塞进媒体分类只会得到破图与坏语音。
也刻意不映射 `mjfree`（梦角自由造句）——那是 `dream-free.js` 程序生成的重造句卡，
客户端自己维护，云端灌进去只会得到上下文无关的句子。

云端那些**还没填内容的空分类**（`items: []`）会被直接跳过，不会建出空分组。

**组与组怎么匹配**——目标分类下按顺序找同名分组，命中即并入，不再并排建第二个：

1. 先找「云端·日常」这类**上一轮云端导入建的组** → 复用，重复导入不会分裂成两个同名组；
2. 再找**你自己建的完全同名分组**「日常」→ 并进去（`CFG.mergeSameNameGroup = false` 可关掉）；
3. 都没有，就**扫其它分类里有没有错位的「云端·日常」**（见下面的分组归位）→ 有就整组搬过来；
4. 还没有，才新建「云端·日常」。

并入时你自己的字卡排在前面，云端内容追加在后面，组内仍然逐条去重。脚本日志会打印
`字卡新增 N 条，并入已有分组 日常/颜文字`。

站点内导入走同一套规则：`【云端·<label>】` 开头的数据块按 label 分流到对应分类，分组名同样
先并同名、再新建。普通手动粘贴（行首 `【组名】` 不带「云端·」前缀）行为不变，仍然落在当前 tab。

#### 分组归位（脚本 1.5.0 起，站点同步）

映射表是**后来才补齐**的：1.3.0 之前没有那 13 个功能分类，1.4.0 之前没有 `poke`（拍一拍）。
在那之前导入过的人，库里会留下「云端·摸鱼」「云端·拍一拍」这些**建在主字卡下的错位组**；
升级后脚本只在目标分类里找同名组，老组没人管，界面上看起来就是「映射改了但没生效，
拍一拍还在主字卡里」。

现在导入时会先把这些错位组**整组搬到它该去的分类**：卡片一张不丢，只是换 tab；组里你自己
加过的内容也一起走（组名已经说明了它属于哪一类）。只搬带「云端·」前缀的组——你自己命名的
「拍一拍」分组不动，避免挪动你的组织架构。日志会打印 `分组归位：云端·拍一拍  text → poke`，
界面提示里会多一句「N 个分组归位到正确分类」。

这条检查**不看云端内容有没有更新**（`mirror.adoptSig`），所以升级后即使云端一个字没变，
第一次打开也会把老库里的错位组搬正一次。

### 旧结构迁移清理（脚本 1.1.0 起）

cy-chat 的字卡在 2026-10 从「一个 `customReplies` 装 1521 条」拆成了七个分类
（`daily` / `connect` / `address` / `quotes` / `sweet` / `kaomoji` / `emoji`）。

旧结构时期，本脚本把这 1521 条写进「云端·自定义回复」一个组。拆分类之后，七个新分类
会各自建组，旧组没人清，于是同一批字卡在库里出现两遍（1521 + 1521）。

1.1.0 起同步时会顺手清理，规则很保守：

- 只有云端**已经是新结构**（出现了 `CFG.legacyWordKeys` 之外的分类）且旧分类已从云端消失，
  才动手；云端若退回旧结构，直接跳过，不会误删。
- 逐条比对内容：组内每一条都能在云端找到 → 判定为旧结构的完整副本，整组删除。
- 只要有一条对不上（你自己往这组里加过东西）→ 保留该组，只摘掉能对上的那些。
- 清理只在「这一版云端数据」上做一次（`mirror.purgeSig`），不会每次开页面都扫库。

日志会打印 `迁移清理：移除旧结构重复字卡 N 条`。如果没看到任何清理日志、但库里确实有
两份，先确认 `CFG.wordMap` 里配的组名和库里旧组的名字是否一致。

> 1.2.0 把七分类都配进了 `wordMap`（为了给它们指定分类和组名），所以「是否已换新结构」的
> 判据改成了 `legacyWordKeys` 白名单——继续用「`wordMap` 里没配的 key」判断会永远判成旧结构，
> 旧组就再也清不掉了。1.3.0 又把 13 个功能分类配进去，同理不影响这条判据（`legacyWordKeys`
> 始终只认 `customReplies` / `pokes` / `statuses` 三条）。

> 1.4.0 的 `poke` 拍一拍**不是**旧结构的 `pokes`：旧组叫「云端·戳一戳」、属于历史迁移清理对象，
> 新组叫「云端·拍一拍」。两条映射同时存在，各自往自己那个组里写，不会互相覆盖，也不会被误清。

### 字卡取源：并发挑最新版本（脚本 1.6.0 起，站点同步）

jsDelivr 的**每个边缘节点各自缓存**，进度并不一致。2026-10-26 实测同一时刻：

| 镜像 | `Word/word.json` |
|---|---|
| `fastly.jsdelivr.net` | v2.1.0 / 20 类 / **没有拍一拍** |
| `gcore.jsdelivr.net` | v2.2.0 / 21 类 / 拍一拍 30 条 |
| `cdn.jsdelivr.net` | v2.2.0 / 21 类 / 拍一拍 30 条 |

更麻烦的是：在 jsDelivr 上加 `?t=` / `?v=` 这类查询参数**完全无效**，仍然命中同一份旧缓存；
唯一可靠的清法是打 purge 接口，或者等它自己刷。

所以「只配一个地址」和「顺序回退，谁先回来用谁」都会踩坑——命中的那个节点滞后，就永远拉不到
新分类，表现是**同一份云端数据，手机能导入拍一拍、电脑不行**。

现在字卡的取源方式改成：

- 并发问 `CFG.wordMirrors` 里的所有镜像（`wordUrl` 仍生效，会被并进这一圈）；
- 按 json 自带的 `version` 挑最高的那份，全部失败才报错；
- 单个镜像 6s 超时（`CFG.mirrorTimeoutMs`），连不上的不会拖住整轮同步；
- 站点侧同一套逻辑（`cloud-import.js` 的 `fetchWordFreshest`），单源超时 4s。

> **必须等所有镜像结算完才定案。** 试过「第一个成功就返回」和「给个 1.2s 汇总窗口」，
> 两种都会更容易选中旧数据——滞后的节点因为缓存命中、响应更快，新鲜节点反而要回源、
> 慢一步，先返回就定案等于每次都选旧的那份。冒烟脚本里当场复现过：命中 fastly、
> 展开只有 7 个分组头（没有拍一拍）。改成等全部结算后，同样的网络条件下命中 gcore、
> 8 个分组头。

自己在导入框里手填了 json 地址时**不走并发**——那是你指定的源，不拿别的镜像去盖它。

## 云端仓库

- 字卡 / 表情：`github.com/fcylz/cy-chat` → 走 jsDelivr（带 `Access-Control-Allow-Origin: *`）
- 曲库：`github.com/fcylz/cy-music` → 走 GitHub Pages（同样带 `ACAO:*`）
- `raw.githubusercontent.com` 取不到字卡那两个 json，别换成它
- ⚠️ **jsDelivr 要用可用镜像**：2026-10-22 实测 `cdn.jsdelivr.net` 在本机网络直接连不上
  （curl 返回 000），`fastly.jsdelivr.net` / `gcore.jsdelivr.net` 正常返回 200。
- ⚠️ **镜像之间还会「版本不同步」**：见上面「字卡取源」一节。字卡现在并发挑 version 最高的，
  不再依赖某一个固定镜像；表情/曲库仍走顺序回退（`CFG.memeUrl` / `CFG.musicUrl`）。

均为**公开**仓库，别放私人内容。
